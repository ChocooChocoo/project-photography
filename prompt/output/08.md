# 08 — Studio-owner subscription lifecycle: assessment and recommended process

**Status: documentation complete, no code changed.** The brief
([`prompt/tasks/08.md`](../tasks/08.md)) required reviewing the `docs` folder before drawing
conclusions, assessing whether the documented lifecycle is complete and correct, and updating
documentation only. It asked for a *recommended process* rather than an option set, so unlike task 07
this pass proposes **one** lifecycle and registers only the genuinely business-level decisions.

Full analysis: [`docs/04-REFERENCE/SUBSCRIPTION LIFECYCLE.md`](../../docs/04-REFERENCE/SUBSCRIPTION%20LIFECYCLE.md).

## 2. The finding that changes the framing

The brief assumes the gap is unclear documentation. The documentation is unclear, but that is the
smaller problem: **the documented lifecycle does not exist, and neither does most of an undocumented
one.**

*A free trial never ends.* The trial branch of
[`SubscriptionController::subscribe()`](../../app/Http/Controllers/StudioOwner/SubscriptionController.php#L145)
writes `trial_ends_at = now() + trial_days` and, two lines later, `end_date = calculateEndDate()` —
which returns `now()->addMonth()` or `addYear()`. Since
[`StudioPlanModel::isActive()`](../../app/Models/StudioPlanModel.php#L124) tests `status`, `end_date`
and `payment_status` and never consults `trial_ends_at`, a 14-day trial on the seeded *Studio Growth*
plan grants **30 days** of fully active access at `amount_paid = 0`; the 30-day trial on the yearly plan
grants **365**. Nothing anywhere compares `trial_ends_at` to the current time in order to change state
— [`NotifyTrialEndingCommand`](../../app/Console/Commands/NotifyTrialEndingCommand.php) is its only
consumer and only writes a notification. That notification tells the owner to *"Add a payment method to
keep your plan active"*; no payment-method screen, route, or column exists. The trial branch also makes
no Stripe call at all, so no card is on file and **the trial cannot convert** even in principle.

*An expired subscription takes nothing away.* [`OwnerMiddleware`](../../app/Http/Middleware/OwnerMiddleware.php#L20)
checks authentication and role only. There is no `app/Policies` directory and no `Gate::` definition in
the application. The single subscription-aware middleware,
[`CheckStudioRegistrationLimit`](../../app/Http/Middleware/CheckStudioRegistrationLimit.php), is
registered on two routes, lets every GET through unconditionally, and blocks the POST only when the
owner already has at least one studio. **The platform's revenue model rests on subscriptions and
nothing on the platform depends on having one.**

## 3. Why the state machine cannot express what is happening

| State | Situation | Reality |
|---|---|---|
| `expired` | Subscription lapsed | **Declared in the enum, written by no code path.** Expiry is implicit, emerging from an `end_date >= now()` filter in three read sites, so a row that lapsed a year ago still reads `active` |
| `past_due` | Renewal charge failed | Does not exist. `paymentFailed()` writes `payment_status = 'failed'` and `status = 'cancelled'` in one action, with no retry, no notice, and no distinction between a declined card and an abandoned Checkout |
| grace | Trial ended, payment pending | Does not exist — no column, no config, no code |
| renewed | Billing period rolled over | Does not exist. `next_billing_date` is written on every row and read by nothing; [`StripeService`](../../app/Services/StripeService.php#L79) builds a Checkout Session in `'mode' => 'payment'` with no Product, Price, customer, or saved card, and no route consumes `verifyWebhookSignature()` |
| reactivated | Owner returns | Does not exist. `subscribe()` creates a brand-new row every time, so history has no continuity |
| `cancelled` | Owner leaves | Half-exists: [`canBeCancelled()`](../../app/Models/StudioPlanModel.php#L168) allows it only within 3 days of `paid_at`. **After day 3 there is no cancellation path at all** — and none for upgrade or downgrade either, since `subscribe()` refuses while an active row exists |

`cancel()` also marks the `tbl_system_revenue` row `refunded` through a direct `update()` rather than
[`markAsRefunded()`](../../app/Models/SystemRevenueModel.php#L290), and calls no gateway — the books say
refunded while the money stays with Stripe.

## 4. Documentation that was wrong, not merely incomplete

Three statements were contradicted by the code and are corrected in place, with dated parentheticals
rather than silent rewrites:

1. **`TECHNICAL ANALYSIS.md` §5.9** and **`NON TECHNICAL ANALYSIS.md` §4.7** both showed studio creation
   gated on an active subscription. **The first studio is free.** The check fires only from the second
   onward, only on POST, and — because the middleware tests `$user->role !== 'owner'` — not at all for
   `owner-super-admin`. Both flowcharts were redrawn.
2. **Roadmap 6.4** specified *"On expiry: downgrade to free tier."* **No free tier exists**:
   `plan_type` is `basic|premium|enterprise` and all eight seeded plans are priced. Struck and
   superseded.
3. **Roadmap 3.4** step 4 (*"During trial period: subscription is active, no payment charged"*) reads
   as a spec but is the defect itself. Annotated, with its remainder moved to Phase 10.

`REVISION CHECKLIST` item 11 ("No free-trial period implemented") was stale rather than wrong — ❌ → ⚠️
with the reason.

## 5. What was recommended

One lifecycle, offered as a default rather than a decision:
`trialing → active → past_due → grace → expired`, with `cancelled` meaning cancel-at-period-end and
`expired → active` on reactivation. Three rules follow: a trial's `end_date` **is** its `trial_ends_at`;
expiry is a written state with a timestamp and a notification, not the absence of a query match; and
cancellation never takes away time already paid for.

On post-expiration handling — the brief's central question — the recommendation is **restrict, never
delete**. Expiry is a billing event, not a moderation action, and deleting an account destroys clients'
booking history, employees' payroll, and the platform's own revenue ledger to punish a lapsed card. The
owner keeps sign-in, every studio, and all historical data with read access, permanently; marketplace
listing, new bookings, and tier-limited editing stop. Bookings a client has already paid for are
honoured to completion whatever the subscription says — which is what forces the access gate to be
capability-scoped rather than a portal lock.

Six decisions are registered as **S1–S6**: grace length, card required at trial start, exactly what
access survives expiry, whether a subscription is scoped to a studio or an owner (the schema says
studio; the middleware and `max_studios` say owner), whether in-flight bookings are honoured, and
whether a free tier exists at all.

## 7. What deliberately did not change

No file under `app/`, `database/`, `resources/`, `routes/`, or `tests/`. The brief limited
implementation to documentation, and every recommended behaviour is either inside a "recommendation,
not a decision" banner or written as a Phase 10 roadmap item — none of it is described as existing.

Specifically left alone despite being found: the trial `end_date` bug, the unwritten `expired` state,
the missing access gate, `notifySubscriptionExpiring()` being dead code, the `owner-super-admin` bypass
in `CheckStudioRegistrationLimit`, and `cancel()` bypassing `markAsRefunded()`. All six are recorded
with file and line so they can be fixed as Phase 10 items rather than as drive-by edits.

## 8. Related defects surfaced, not fixed

1. `tbl_freelancer_plans` has **no `trial_ends_at` column** — the 3.4 migration touched the studio table
   only. There is no freelancer subscribe controller, route, or checkout path at all, yet the catalog
   sells four freelancer plans with trial days on two of them.
2. `Admin\SubscriptionController::edit()` renders `admin.edit-subscription-plans`, a view that does not
   exist, so `trial_days` is write-once at plan creation. (Pre-existing, already recorded under 3.4.)
3. Every seeded studio plan sets `max_studios = 1`, so with seed data the multi-studio gate — the only
   subscription check on the platform — can never pass on any plan.
4. Booking commission works with no subscription at all. Whether an unsubscribed studio should generate
   platform revenue has never been posed as a question.
5. Studio HR, finance and photographer staff sign in through their own portals, and no document states
   whether their access follows the owner's subscription status.

## Before and after, in non-technical terms

*This section is written for readers who need to understand what changed without
reading code — panel members, advisers, and studio owners. Everything after it is
technical evidence.*

### The one-paragraph version

The platform used to have a chatbot that could only repeat answers someone had
typed into it beforehand. If a client asked a question in words the system did
not recognize, it gave up. That chatbot has been replaced with a real AI
assistant that reads the question, understands it, and writes an original answer
using the studio's live package and pricing data. The assistant is deliberately
fenced in: it will only discuss photography services, it refuses abusive or
manipulative messages, and it cannot be talked into revealing the system's
internal information. Studio owners no longer write the replies — they supply
background facts about their studio, and the assistant does the writing.

### How it worked before

The old chatbot was a **matching machine**. Think of it as a filing cabinet of
prepared answer cards. Each card had two sides:

- **Front:** a list of trigger words — for example `price`, `pricing`, `how
  much`, `magkano`, `rate`, `cost`
- **Back:** the exact reply to send if any of those words appeared

When a client typed a message, the system scanned it for trigger words, found
the best-matching card, and sent back whatever was written on the back of that
card — word for word, every single time.

**What the studio owner had to do.** Everything. The owner was effectively the
chatbot's scriptwriter: think of every topic a client might ask about, brainstorm
every possible way a client might phrase it, write the exact reply word for word,
optionally attach clickable buttons that jumped to other prepared cards, and keep
all of it updated whenever prices or services changed. The seeded starter set had
five topics with roughly twenty-two trigger phrases each — over a hundred phrases
hand-written to cover five subjects.

**Where it fell down:**

- **It only knew the words it was given.** A client asking "do you have anything
  for a small barangay wedding under 40k?" would fail — none of those words were
  on any card, so they got the generic "sorry, I didn't understand" message.
- **Every answer was frozen text.** If the studio raised its prices, the old
  reply still quoted the old prices until someone edited the card by hand. The
  chatbot had no connection to the actual package list in the system.
- **It could not combine facts.** Ask two things in one sentence — "how do I book
  and how much is it?" — and it picked one card and ignored the rest.
- **It could not follow a conversation.** Ask "how much?" then "what about for
  two days?" and the second question was treated as if the first never happened.
- **The button system was busywork.** Owners hand-drew a menu tree by wiring
  cards to each other. Clients who did not click the buttons — most of them — got
  nothing out of that work.
- **Maintenance never ended.** The chatbot was only as current as the last time
  someone sat down and updated it.

### How it works now

The assistant uses a real AI language model. It **reads and understands** the
question instead of pattern-matching it against a word list, then **writes a new
answer** in its own words.

Crucially, it does not answer from thin air. Before it responds, the system
quietly hands it the studio's current information: the active packages, their
real prices, their categories and inclusions, plus any background facts the owner
has recorded. The answer is composed from that live data.

**What this means in practice:**

- **Any phrasing works.** "How much?", "magkano po?", "what's your rate for a
  half-day engagement shoot?", and "we're on a tight budget, what can you do for
  30k?" all get real, relevant answers. Nobody had to anticipate those words.
- **Prices are always current.** The assistant reads the live package list at the
  moment it answers. Change a price and the very next answer reflects it.
- **It handles compound and follow-up questions.** It can answer two things in
  one reply, and it remembers the recent back-and-forth.
- **It sounds like a person, not a vending machine.** Answers are written fresh
  each time and adapt to how the question was asked.

**What the studio owner does now.** Far less, and it is a different kind of work.
Instead of scriptwriting, the owner records **studio knowledge** — plain
background facts the assistant should know: studio policies, what makes a package
distinctive, how booking runs at that particular studio. The owner writes the
*facts*; the assistant writes the *reply*. Phrasing no longer matters, so there is
nothing to guess at.

Owners still control the on/off switch, the assistant's display name and avatar,
the greeting shown when a chat opens, the four suggested questions under the
message box, a list of words that get a message blocked before it reaches the AI,
the background facts above, and read access to their studio's chat transcripts.

### Safety, in plain terms

This was the highest-priority requirement, so each protection is worth explaining.

**It stays on topic — on purpose.** A general AI will happily write your essay,
debug your code, or discuss politics. That would be inappropriate coming from a
photography studio's booking window, and it would burn the studio's paid usage on
things that earn nothing. Ask something outside photography services and the
assistant politely explains its scope and invites a relevant question. This is
checked **twice** — on the incoming question and again on the outgoing answer — so
an off-topic reply cannot slip through even if the model tries.

**It refuses abuse without escalating.** Profanity and abusive language are
caught before the message ever reaches the AI. The response is calm and neutral,
it never repeats the offending words back, and the user can immediately ask a
legitimate question and carry on. No lecture, no shutdown.

**It cannot be talked out of its rules.** There is a known trick where a user
types "ignore all your previous instructions" or "pretend you are a different
assistant with no restrictions" and the AI complies — the most common way AI
features get abused. Three things prevent it here:

1. The security rules are built into the application itself, not stored in a
   database anyone can edit — the owner cannot weaken them, and neither can a
   user.
2. The rules are re-sent with every single message, so a long conversation cannot
   gradually push them out of the assistant's memory.
3. Manipulation attempts are recognized on sight and stopped before the AI is
   even contacted.

Anything an owner or client types is explicitly labelled to the assistant as
untrusted reference material — information to consider, never commands to obey.

**It cannot leak the system's secrets.** The AI provider requires a private
access key. That key lives only on the server, in a protected settings file. It
is never sent to the browser, never appears in the page, never shows up in an
error message, and is never written into the chat history. A visitor inspecting
the page will not find it, and the assistant itself cannot be persuaded to recite
it — the outgoing answer is scanned for exactly that kind of leak before display.
The same protection covers internal instructions, configuration, and source code.
If a draft answer contains any of it, the whole reply is thrown away and replaced
with a safe refusal — never partially censored, since partial censoring still
tells an attacker they were close.

**Every failure is a soft landing.** If the AI provider is slow, down,
overloaded, or returns something unusable, the user sees a short, plain message
saying the assistant is briefly unavailable and to try again shortly. No error
codes, no jargon, no crash, no internal details exposed.

**Privacy was tightened along the way.** Three genuine problems in the existing
chat code were found and fixed: anyone signed in could read anyone else's chat
transcript; internal error details were being sent to the browser; and a studio
owner could edit another owner's chatbot entries. None were caused by the AI
work — all three were pre-existing and are now closed.

### Honest limitations

**There is a usage ceiling.** The AI provider's free tier allows a fixed amount
of work per minute, and the security rules must be re-sent with every message —
non-negotiable, since trimming them is exactly how these systems get compromised.
The practical effect is roughly **three to five assistant replies per minute
across the entire platform** before users are told to wait a moment. Comfortable
for a capstone demonstration; a busy live deployment would need a paid provider
plan. That is a budget decision, not a technical obstacle, and it can be raised
without touching the code. The technical detail is in *Two things worth your
attention* below.

**One item was left for the project owner to action.** The project's environment
file — which holds private access keys for the payment providers and now for the
AI provider — was committed into version control early in the project's life,
before the rule excluding it took effect. Those keys are therefore in the
project's history. This was not introduced by this work, but it conflicts with
the requirement that credentials never enter source control. It was deliberately
not "fixed" quietly, because the real remedy is to **replace the affected keys**,
a decision with billing and downtime consequences that belongs to the project
owner. Details below.

### Security fixes found while working in this code

- **Conversation transcripts were readable by any authenticated user.** `session_id` was never checked against `Auth::id()`, so anyone could read anyone's chat history. Now enforced on every message, end, history, and feedback call (403 with neutral copy). Regression test: `test_chatbot_session_ownership_is_enforced`.
- **Exception messages leaked into JSON responses.** Every `catch` block returned `$e->getMessage()` to the browser. Now fixed generic copy; the cause goes to the log only.
- **Owner knowledge entries had no ownership scoping.** `updateIntent`, `deleteIntent`, and `toggleIntentStatus` used bare `findOrFail($id)`, so one owner could edit another's rows. Now scoped through the owner's own config.

## Two things worth your attention

### 1. `.env` is tracked in git — rotate the exposed keys

`.gitignore` lists `.env`, but the file was committed before that took effect, so
the ignore rule does nothing and **live PayMongo, Stripe, and now Groq keys are
in the repository's history**. This directly contradicts the task's requirement
that credentials never be committed to source control. I did not change the
index — remediation is yours to sequence, because rotation has to come with it:

```bash
git rm --cached .env
```

Then commit, and **rotate every key that has been in that file** — PayMongo,
Stripe, and Groq. Untracking stops future commits but does not remove the values
from existing history, so rotation is the only real fix.

### 2. The model's reasoning had to be turned off

`qwen/qwen3.6-27b` is a reasoning model. At Groq's defaults it writes its chain
of thought into the reply body: a one-sentence answer cost 624 tokens instead of
40, the real answer was truncated at `max_tokens`, and the visible reasoning
restated the security rules — which the output guard correctly threw out as an
instruction echo. The first live test therefore refused a perfectly legitimate
"what wedding packages do you offer?" question.

Fixed by sending `reasoning_format: parsed` and `reasoning_effort: none` (both
configurable, sent only when non-empty). Confirmed working end to end afterwards.

**Throughput consequence.** The security rules are ~650 tokens on their own and
are not negotiable, so a request costs 1,300–2,100 tokens depending on whether
package detail is injected. Against the 8,000 tokens-per-minute tier that is
roughly **3–5 assistant messages per minute across the whole platform** before
users see the `rate_limited` fallback. Mitigations already applied: package rows
are injected only for pricing questions (others get a one-line summary), package
rows capped at 10 with descriptions truncated, knowledge entries capped at 6,
history capped at 6 messages / 3,000 characters. If more headroom is needed,
raise the Groq tier or lower those limits — do not trim the security rules.

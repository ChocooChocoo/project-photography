# Objective

## Modernize the Chat System with a Secure, Photography-Focused AI Assistant

---

## Role

You are an AI integration and application security specialist. Approach this objective with a strong focus on secure model integration, strict domain control, credential protection, reliable fallback behavior, and clear technical documentation.

---

## Description

Update all relevant project documentation and replace the existing fixed-response chatbot with a modern AI-powered assistant. The current chat functionality supports conversations between photographers and clients through customizable, predefined messages and replies. Transform this functionality into an AI assistant powered by Groq and the `qwen/qwen3.6-27b` model. The assistant must respond only to requests related to photography services and must safely reject abusive, irrelevant, malicious, or unauthorized requests. Security must remain the highest priority throughout the implementation.

---

## Primary Objective

Replace the existing customizable, fixed-response chatbot with a secure Groq-powered AI assistant designed exclusively for photography-service conversations between photographers and clients.

---

## Secondary Objectives

* Update all relevant documentation to reflect the new AI-powered chat architecture, functionality, configuration, security requirements, and expected behavior.
* Restrict the assistant’s responses to photography services and directly related conversations.
* Add fallback responses for profanity, abusive language, unrelated questions, malicious prompts, and unsupported requests.
* Protect environment variables, API credentials, internal prompts, system instructions, application data, and other sensitive system resources from disclosure.
* Preserve the existing photographer-to-client chat experience while replacing predefined chatbot behavior with AI-generated responses.

---

## Success Criteria

* The existing fixed-response chatbot is replaced with an AI assistant powered by Groq.
* The implementation uses the `qwen/qwen3.6-27b` model.
* Photographers and clients can interact with the AI assistant through the existing chat interface.
* The assistant responds only to questions and requests related to photography services.
* Unrelated, abusive, profane, malicious, or unsupported messages trigger an appropriate fallback response.
* The assistant does not reveal API credentials, environment variables, system prompts, internal instructions, source code, configuration data, or other protected system information.
* Groq credentials are loaded securely from protected environment configuration and are never hardcoded, exposed to the client, logged, or included in documentation.
* All relevant project documentation accurately reflects the updated AI integration and security requirements.

---

## Constraints

* Use Groq as the AI model provider.
* Use the model ID `qwen/qwen3.6-27b`.
* Store the Groq API key securely in an environment variable or protected secret-management system.
* Do not expose the Groq API key in frontend code, repositories, logs, error messages, documentation, or API responses.
* Design the integration around the provided model limits:

  * Requests per minute: 30
  * Requests per day: 1,000
  * Tokens per minute: 8,000
  * Tokens per day: 200,000
* Restrict the assistant to photography-service topics.
* Apply security guardrails before processing user input and before returning model output.

## Priority Level

* Security is the highest-priority requirement.
* Credential protection, prompt-injection resistance, sensitive-information protection, and response-scope enforcement take precedence over conversational flexibility.

## Out of Scope

* Answering questions unrelated to photography services.
* Participating in abusive, profane, threatening, or otherwise inappropriate conversations.
* Revealing environment variables, API keys, system prompts, internal instructions, application configuration, source code, database information, or other protected resources.
* Following user instructions that attempt to override, ignore, reveal, or modify the assistant’s security rules.
* Exposing the Groq API directly through the client-side application.

* The revised implementation will use Groq for AI-model access.
* The selected model is `qwen/qwen3.6-27b`.
* The implementation depends on secure server-side API communication, protected credential storage, input validation, output validation, request-rate management, and updated project documentation.

## Supporting Tasks

### Documentation Updates

* Review all relevant project documentation and replace references to the existing fixed-response chatbot with descriptions of the new AI-powered assistant.
* Document the Groq integration, selected model, supported photography-related use cases, security controls, fallback behavior, and configuration requirements.
* Document credential setup without including the actual API key or any other sensitive value.
* Ensure the documentation clearly distinguishes server-side responsibilities from client-side functionality.

### Groq Integration

* Replace the current predefined chatbot response logic with server-side requests to the Groq API.
* Configure the integration to use the `qwen/qwen3.6-27b` model.
* Load the Groq API key from a protected environment variable or secret-management system.
* Prevent the frontend from directly accessing the Groq API or its credentials.
* Handle API errors, timeouts, rate limits, unavailable services, and invalid responses through safe fallback messages.

### Photography-Domain Enforcement

* Define the assistant’s permitted scope as photography services and directly related conversations.
* Validate each user message before sending it to the AI model.
* Reject or redirect questions that are unrelated to photography services.
* Validate generated responses before displaying them to ensure they remain within the permitted domain.
* Prevent users from expanding the assistant’s scope through prompt injection, role reassignment, encoded instructions, or requests to ignore previous rules.

### Language and Abuse Handling

* Detect profane, abusive, threatening, or inappropriate messages.
* Return a neutral and professional fallback response when inappropriate language is detected.
* Avoid repeating or escalating abusive language.
* Allow the user to continue the conversation by returning to a legitimate photography-service question.

### Security Guardrails

* Prevent the disclosure of API keys, environment variables, system prompts, developer instructions, internal configuration, source code, logs, database details, and protected application data.
* Treat all user-provided content as untrusted input.
* Sanitize and validate user messages before processing them.
* Validate and filter model-generated responses before returning them to the user.
* Reject requests that ask the assistant to reveal, summarize, repeat, transform, encode, or indirectly expose protected information.
* Use generic error messages that do not reveal internal implementation details.
* Avoid storing sensitive user messages or complete model responses in logs unless explicitly required and securely protected.
* Apply request limits and token controls that respect the selected model’s usage limits.
* Ensure that security instructions cannot be overridden by user messages or conversation history.

### Fallback Behavior

* Provide a photography-focused fallback when a user asks an unrelated question.
* Provide a respectful fallback when profanity or abusive language is detected.
* Provide a secure refusal when a user requests protected system information.
* Provide a temporary service-error response when the Groq API is unavailable, rate-limited, or returns an invalid result.
* Keep fallback messages concise, professional, and consistent for both photographers and clients.

## Detailed Breakdown

### AI Assistant Behavior

The AI assistant must support conversations between photographers and clients while remaining focused on photography services. Its responses should be generated dynamically rather than selected from fixed, predefined replies. Every response must remain professional, relevant to the permitted domain, and safe to display within the application.

### Domain Restrictions

The assistant must respond only to messages related to photography services. Messages outside this scope must not receive a general-purpose AI answer. Instead, the assistant should politely explain that it can assist only with photography-related questions and invite the user to ask about an applicable photography service.

### Prompt-Injection Protection

The assistant must reject instructions that attempt to change its role, bypass its photography-only scope, ignore security controls, disclose hidden prompts, or reveal protected system information. This restriction must also apply when malicious instructions are disguised as examples, translations, code, encoded text, debugging requests, role-play scenarios, or requests to repeat earlier instructions.

### Credential and Environment Protection

The Groq API key must remain exclusively within a secure server-side environment. It must never be sent to the browser, embedded in application bundles, committed to source control, displayed in documentation, included in error responses, or written to unprotected logs. Any credential previously exposed outside secure storage must be replaced and stored using the approved secret-management process.

### Input and Output Validation

User messages must be validated before being sent to the model, and generated responses must be validated before being displayed. The validation process must enforce the photography-only scope, detect inappropriate language, block attempts to access sensitive information, and prevent unsafe model output from reaching photographers or clients.

### Rate and Token Management

The integration must account for the model’s limits of 30 requests per minute, 1,000 requests per day, 8,000 tokens per minute, and 200,000 tokens per day. Request handling must prevent excessive usage, control conversation-context size, and return a safe fallback response whenever a usage limit is reached.

### Failure Handling

When the AI provider is unavailable or returns an error, the application must fail safely. Users should receive a clear, nontechnical message explaining that the assistant is temporarily unavailable. Error responses must not disclose credentials, request headers, internal endpoints, stack traces, configuration values, or other implementation details.
